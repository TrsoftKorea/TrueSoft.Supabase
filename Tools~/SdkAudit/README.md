# SDK 규칙 정적 검사

`CLAUDE.md`의 SDK·문서 규칙 중 **컴파일러가 잡아주지 않는 것**을 Unity 없이 검사하는 도구입니다.

## 왜 필요한가

이 SDK에서 조용히 새 나가는 위반은 대체로 이렇습니다.

- **공개 표면** — `Supabase` 파사드에 `internal` 멤버가 섞이거나, 공개 메서드가 result 타입이 아닌 값을 돌려주는 경우. 컴파일은 통과하고 게임이 쓰기 시작한 뒤에야 문제가 됩니다.
- **리셋 누락** — 파사드 백킹 필드를 추가하면서 리셋 블록에 넣는 걸 빠뜨리는 경우. 계정을 바꿔도 이전 상태가 남습니다.
- **문서 드리프트** — 없는 API를 가리키거나, 시그니처·기본값이 바뀐 뒤 문서가 그대로 남는 경우.
- **샘플 부패** — `Samples~`는 import 전까지 컴파일되지 않아 API가 바뀌어도 아무도 모릅니다.
- **설치 순서** — `install.sql`은 빈 프로젝트에 위에서 아래로 한 번 실행됩니다. 뒤 절의 객체를 앞 절이 참조하면 **신규 프로젝트에서만** 실패하고 라이브 DB에서는 드러나지 않습니다.

## 사용법

```sh
dotnet run --project Tools~/SdkAudit
```

- 종료 코드 `0` = 통과. `1` = 오류.
- 경고는 종료 코드에 영향을 주지 않습니다. 판단이 필요한 항목입니다.

작업이 끝날 때 `.claude/settings.json`의 Stop 훅이 자동으로 돌립니다.

```sh
dotnet run --project Tools~/SdkAudit -- --if-changed
```

`--if-changed`는 `git status`를 보고 **검사 대상 경로가 바뀌지 않았으면 아무 일도 하지 않습니다.** 대화만 한 턴에는 비용이 거의 없고, 파일을 고친 턴에는 잊지 않고 돕니다. 조건 판정을 셸이 아니라 검사기 안에서 하는 이유는 플랫폼마다 훅 셸이 다르기 때문입니다.

감시 경로는 `ChangeGate.Watched`에 있습니다. 검사 대상을 늘리면 여기도 함께 늘립니다.

**검사기를 고쳤으면 자체 테스트를 함께 돌립니다.**

```sh
dotnet run --project Tools~/SdkAudit -- --selftest
```

위반만 모아둔 임시 리포지토리를 만들어 돌리고, **각 규칙이 실제로 발동하는지** 확인합니다. 규칙 하나를 고치다 다른 규칙의 탐지를 조용히 망가뜨리는 것을 잡습니다.

필요한 이유는 겪어봤기 때문입니다. 소비 게임 검사(R12)를 처음 붙였을 때 경로 필터가 너무 넓어 **아무것도 잡지 못했는데, "통과"만 봐서는 알 수 없었습니다.** 통과가 곧 동작을 뜻하지는 않습니다.

새 규칙을 추가하면 `SelfTest.ExpectedTags`에 태그를 넣고 픽스처에 위반 사례를 추가합니다.

## 작동 방식

세 가지 방식을 씁니다.

**C# — Roslyn 구문 파싱.** `Runtime/`의 모든 `.cs`를 파싱합니다. 컴파일이 아니라 파싱이라 `UnityEngine` 어셈블리가 필요 없고, 그래서 `Runtime/Unity`까지 볼 수 있습니다. 정규식으로 소스를 긁는 것과 달리 주석·문자열 안의 코드처럼 보이는 텍스트에 속지 않습니다. 대신 **타입 해석이 없어** 반환 타입 판정은 이름 문자열 비교입니다.

**리셋 블록 — 이름이 아니라 행동으로 찾기.** `Initialize`를 하드코딩하면 이름이 바뀌는 순간 검사가 무력화됩니다. 대신 파사드 필드를 `null`로 되돌리는 개수를 세어 **가장 많은 메서드를 리셋 블록으로** 봅니다.

**문서·SQL — 줄 단위 텍스트 스캔.** 마크다운은 ` ```csharp ` 펜스 안/밖 상태를 추적하며 봅니다. SQL은 달러 인용(`$$ … $$`) 함수 본문과 주석을 **같은 길이의 공백으로 덮어** 오프셋을 보존한 뒤 참조를 찾습니다. 함수 본문은 설치 시점에 해석되지 않으므로 순서 검사 대상이 아니기 때문입니다.

## 검사 대상 파일

| 대상 | 적용 규칙 |
|------|-----------|
| `Runtime/`·`Samples~/` | R1·R2·R6·R7·R11 |
| `docs~/guide/**/*.md` | R3·R4·R5·R8·R10·R15 |
| `CLAUDE.md`·`.claude/skills/**`·`.claude/rules/**` | **R3·R4·R8(사유)만**. `CLAUDE.md`는 R14도 |
| `install.sql` | R9·R13 |
| `consumers.txt`에 적힌 게임의 `Assets/Scripts` | R12 |

규칙 파일을 보는 이유는 게임 문서보다 위험하기 때문입니다. **문서가 틀리면 게임 개발자가 고생하지만, `CLAUDE.md`가 틀리면 Claude가 읽고 그대로 코드를 고칩니다.** 실제로 "SupabaseSDK는 MonoBehaviour singleton"이라는 한 줄 때문에 샘플 컴파일이 깨진 적이 있습니다.

형식 규칙(R5·R10)은 VitePress 페이지 전제라 규칙 파일에 적용하지 않습니다. `SupabaseErrorCode` 노출 금지도 마찬가지입니다 — 규칙 파일은 SDK 내부 카탈로그를 설명하는 자리입니다.

### 소비 게임

게임은 SDK를 GitHub UPM으로 참조합니다. **공개 API를 지우거나 시그니처를 바꾸면 게임이 깨지는데, 이 리포지토리만 봐서는 드러나지 않습니다.** `consumers.txt`에 게임 경로를 적으면 그 프로젝트의 `Assets/Scripts`를 함께 봅니다.

경로는 리포지토리 루트 기준 상대 경로 또는 절대 경로이고, 없는 경로는 경고만 남기고 건너뜁니다. 다른 PC에서 폴더 구조가 다르면 이 파일만 고치면 됩니다.

`Assets/Samples`는 보지 않습니다 — import된 SDK 샘플 사본이라 원본을 R6이 이미 봅니다. `.claude/worktrees`도 제외합니다.

## 예외 처리

검사기가 규칙의 예외를 알고 있어야 오탐이 나지 않습니다. 현재 반영된 예외는 다음과 같습니다.

| 예외 | 이유 |
|------|------|
| `CodeRules.NonFailingMembers` | 값을 돌려주지만 실패할 수 없는 멤버(순수 변환·등록 헬퍼). 항목을 추가할 때는 근거를 주석으로 남기세요 |
| `[Supabase.Chat]` 형태 | 로그 태그이지 멤버 참조가 아닙니다 |
| `TrueSoft.Supabase.git` 형태 | 한정자가 붙은 이름은 멤버 참조가 아닙니다 |
| 이미지가 있는 페이지의 `---` | 단계별 절차 페이지의 단계 구분은 허용됩니다 |
| `alter table if exists` | 신규 설치에서 no-op인 마이그레이션 구문이라 선행 정의가 필요 없습니다 |
| `$$ … $$` 함수 본문 | 설치 시점에 해석되지 않아 순서와 무관합니다 |
| 다른 스키마(`auth.`·`cron.`) | `public`만 검사합니다 |
| `Supabase.Xxx()`·`SupabaseReason.멤버명`·`Supabase.Try*` | 규칙 문서가 형식을 설명할 때 쓰는 자리표시자입니다 |
| `SupabaseReason.cs` | 파일명입니다. 사유 표기는 대문자로 시작하는 것만 봅니다 |
| R15에서 `##` 2개 이상인 페이지 | 다중 절 페이지는 첫 절에도 제목이 있어야 책갈피 최상단이 빠지지 않습니다. 그것까지 잡으면 오탐이 됩니다 |

## 정기 점검 체크리스트

이 검사기는 SDK 정기 점검의 **자동화 가능한 부분**만 담당합니다. 전체 점검은 아래 축으로 돕니다.

| 축 | 자동화 | 방법 |
|----|--------|------|
| 규칙의 모순·모호 제거 | ✕ | `CLAUDE.md`를 코드와 대조 |
| 규칙 위반 수정 | 일부 | R1~R15가 기계적 위반 담당. 로그 레벨 분류는 수동 |
| 미사용 코드 제거 | 일부 | R7은 파사드만. 전체는 선언 이름 × 참조 수 전수 조사 |
| 중복 코드 제거 | ✕ | 판단 필요 |
| 비효율 코드 개선 | ✕ | 판단 필요 |
| 문서-코드 불일치 | 일부 | R3·R4·R8은 이름·시그니처·기본값. 서술 내용은 수동 |
| 문서 레이아웃·통일성 | 일부 | R5는 형식, R10·R15는 구조. 톤은 수동 |
| 공개 표면 | ○ | R1 + 공개 타입 목록 검토 |
| 초기화·리셋 대칭성 | ○ | R2 |
| 샘플 최신성 | ○ | R6 |
| 소비 게임 호환성 | ○ | R12 |
| DB 정합성 | 일부 | R9는 `install.sql` 설치 순서, R13은 cron 등록 누락. 라이브 DB 대조는 Supabase MCP 필요 |

**축은 하나씩 끊어서 돌립니다.** 한 번에 여러 축을 건드리면 무엇이 무엇을 깨뜨렸는지 가릴 수 없습니다. 특히 미사용·중복·비효율 축은 동작을 바꿀 수 있어 Unity 재컴파일과 Play Mode 확인이 붙으므로 마지막에 둡니다.

### 미사용 코드 전수 조사

R7이 못 보는 범위(내부 멤버·Core)는 이렇게 훑습니다.

```sh
cat $(find Runtime Editor "Samples~" -name "*.cs") > corpus.tmp
cat $(find docs~/guide -name "*.md") >> corpus.tmp
```

선언 이름을 뽑아 `corpus.tmp`에서 등장 횟수를 세고, **1회(선언뿐)인 것**을 후보로 봅니다. Unity 매직 메서드·`[RuntimeInitializeOnLoadMethod]`·`UnitySendMessage` 대상·인터페이스 구현은 오탐이므로 걸러냅니다.

## 한계 — 자동화 대상이 아닌 것

판단이 필요해 사람이 봐야 하는 항목입니다.

- 규칙 자체의 모순·모호성
- 중복 코드, 비효율 코드
- 에러 사유의 로그 레벨 분류(`IsExpectedFailureReason`) — "누구 탓인가"는 기계가 못 정합니다
- 라이브 DB와 `install.sql`의 대조 — Supabase MCP가 필요합니다
- 문서 **서술**의 정확성 — 검사기는 이름이 존재하는지만 봅니다. "이 함수는 ~한다"가 맞는지는 사람이 읽어야 합니다
- 표 칸의 **부연 괄호** — 수식 표기 `(i)`·버전 `(4.x)`·파라미터 목록과 구분할 수 없어 자동 검사를 넣었다 뺐습니다. 하위 유형 구분은 가운뎃점(·)으로 손보세요

## Unity 영향

폴더명이 `~`로 끝나 Unity가 완전히 무시합니다(`.meta` 미생성).
