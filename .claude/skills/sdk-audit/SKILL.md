# SDK 점검

점검에는 두 방향이 있다. **무엇을 찾으려는지에 따라 고른다.**

| 방향 | 훑는 단위 | 잡는 것 |
|------|-----------|---------|
| **가로 — 축 점검** | 규칙 하나를 SDK 전체에 | 규칙 위반, 죽은 코드, 중복 |
| **세로 — 기능 점검** | 기능 하나를 계층 전체에 | 계층 사이 이음매의 어긋남 |

가로는 "규칙을 지켰나", 세로는 "이 기능이 앞뒤가 맞나"를 본다. **둘은 서로 다른 것을 잡는다.** 로그아웃 때 채팅 구독이 안 끊기던 버그는 규칙 위반이 아니라 이음매 문제라, 가로 점검에서는 우연히 걸렸다.

## 시작할 때

1. **검사기부터 돌린다.** 현재 무엇이 깨져 있는지가 출발점이다.

```bash
dotnet run --project Tools~/SdkAudit
dotnet run --project Tools~/SdkAudit -- --selftest
```

작업 중에는 Stop 훅이 `--if-changed` 로 자동 실행하므로 매번 손으로 부를 필요는 없다. 다만 **점검을 시작할 때는 전체를 한 번 돌려 기준선을 잡는다** — 훅은 바뀐 게 있을 때만 돌기 때문이다.

2. **지난 회차 진행 상태를 확인한다.** 메모리의 `project_sdk_audit_progress.md`에 끝난 축·남은 축·결정 대기 항목이 있다.

3. **방향과 대상을 사용자와 합의한다.** 임의로 여러 개를 한꺼번에 건드리지 않는다.

## 한 번에 도는 방식이 기본이다

축·기능마다 멈춰 확인받지 않는다. **멈춤은 검증 경계에서만 만든다** — 3회차에서 멈춘 6번 중 5번이 Unity 재컴파일과 Retool 게시 때문이었고, 축을 쪼갠 것 자체가 이유였던 적은 없다.

네 단계로 돈다.

| 단계 | 하는 일 | 멈춤 |
|------|---------|------|
| 1 조사 | 대상 전부를 훑는다. **아무것도 고치지 않는다** | 없음 |
| 2 합의 | 발견 목록을 3분류해 **한 번에** 제시 | 여기 1회 |
| 3 적용 | 아래 순서대로 고친다 | 없음 |
| 4 검증 | 재컴파일·게시·배포를 **한 번에** 넘긴다 | 여기 1회 |

**3단계의 순서가 핵심이다. 검증할 수 없는 것을 뒤로 민다.**

1. 문서·규칙·검사기 — `SdkAudit`·`vitepress build` 로 즉시 검증된다
2. `install.sql`·Edge Function — 라이브 조회로 즉시 검증된다
3. `Runtime/Core` — `CoreCompileCheck` 로 즉시 검증된다
4. `Runtime/Unity`·`Editor` — **검증 수단이 없다. 반드시 마지막.**

**축마다 커밋을 권한다.** 마지막 재컴파일이 실패해도 어느 축이 깨뜨렸는지 바로 좁혀진다 — 한 번에 도는 방식의 유일한 약점이 이걸로 사라진다.

세로(기능) 점검은 원래 기능 단위로 관통하므로 여러 기능을 이어서 돌아도 된다. 기능 사이에 멈추지 않는다.

## 공통 규칙

**조사와 수정을 분리한다.** 조사는 시간이 예측되지만 수정은 발견량에 달렸다. 그래서 계획은 "무엇을 고칠지"가 아니라 **"무엇을 훑을지"**로 세우고, 수정 견적은 발견 목록을 본 뒤에 낸다.

**발견은 즉시 고치지 말고 3분류한다.**

| 분류 | 처리 |
|------|------|
| 즉시 수정 | 원인이 명확하고 한 파일에서 끝나는 것 |
| 결정 대기 | 판단이 갈리는 것. **모아뒀다가 묶어서 물어본다** — 하나씩 물으면 진행이 끊긴다. 대상마다 멈추지 않는 대신 메모리에 적고, **대상을 다 돈 뒤 목록을 통째로 제시한다.** 안 꺼내면 그냥 잊힌다 |
| 이월 | 고치는 데 기능 하나 만드는 만큼 드는 것. 별도 항목으로 빼고 진행 |

**대상 하나당 조사 시간 상한을 둔다.** 넘으면 발견 목록만 남기고 다음으로 넘어간다. 다 못 도는 걸 전제로 순서를 정해두는 것이 계획의 핵심이다.

## 가로 — 축 점검

축 목록과 자동화 범위는 `Tools~/SdkAudit/README.md`의 "정기 점검 체크리스트"에 있다.

**축은 이어서 돌되 적용 순서를 지킨다**("한 번에 도는 방식이 기본이다" 참고). 동작을 바꾸는 축(미사용·중복·비효율)은 검증 수단이 없으므로 문서·규칙 축을 먼저 정리한 뒤 마지막에 몰아서 적용한다. **축마다 커밋**해 두면 마지막 재컴파일이 실패해도 범인을 바로 좁힐 수 있다.

한 축 안에서는 이 순서로 한다.

1. **전수 조사부터 한다.** 고치기 전에 무엇이 나왔는지 목록으로 남긴다.
2. **오탐을 걸러낸다.** 검사기가 낸 경고라도 규칙의 정당한 예외일 수 있다.
3. **명확한 것만 고친다.**
4. **검증한다.** 보고는 모든 축이 끝난 뒤 한 번에 한다.

**축 사이에 겹치는 것을 놓치지 말 것.** 중복을 걷으면 죽은 코드가 새로 생기고(3회차에서 `CallRpcAsync` 통합이 포워더 6개를 죽였다), 구조를 바꾸면 규칙 문서가 낡는다. 이어서 돌면 그 자리에서 잡히지만, **한 축을 끝냈다고 앞 축을 다시 안 보면 놓친다.**

## 세로 — 기능 점검

데이터가 흐르는 방향으로 따라간다.

```
install.sql → Core 서비스 → Facade → Supabase 파사드 → 문서 → 샘플 → Retool
```

계층을 따로 읽지 말고 **인접한 두 계층의 이음매**를 본다. 오류는 계층 안이 아니라 이음매에서 난다.

| 이음매 | 보는 것 |
|--------|---------|
| DB ↔ Core | RPC 이름·인자·반환 형태가 `install.sql`과 맞나. 서버가 던지는 에러 문자열이 카탈로그에 있나 |
| Core ↔ Facade | 세션·토큰 없을 때 처리, 실패 사유가 그대로 보존되나 |
| Facade ↔ 파사드 | 게임에 필요한 게 다 나왔나, 안 나와야 할 게 나왔나 |
| 코드 ↔ 문서 | **그 API가 실제로 낼 수 있는 사유가 에러 코드 표에 다 있나.** 동작 서술이 구현과 맞나 |
| 코드 ↔ 샘플 | 샘플이 주요 경로를 실제로 밟나 |
| 코드 ↔ Retool | 운영 화면이 쓰는 RPC·컬럼이 실제로 있나 |

### 문서 서술은 주장을 뽑아 대조한다

검사기는 **이름이 실존하는지만** 본다. "이 함수는 ~한다"가 맞는지는 사람이 읽어야 하는데, **그냥 읽으면 못 잡는다.** "SupabaseSDK는 MonoBehaviour singleton"이라는 오기는 매 세션 읽히던 문장인데도 무언가를 깨뜨리고 원인을 찾으러 갔을 때에야 보였다. 자기가 쓴 문장은 쓴 의도가 보이지 문장이 안 보인다.

그래서 읽으면서 판단하지 말고 **검증 가능한 주장을 먼저 목록으로 뽑는다.**

| 주장 유형 | 예 |
|-----------|-----|
| 타입·구조 | "X는 MonoBehaviour다", "X는 internal이다" |
| 자동 동작 | "로그인 시 자동으로 정리된다" |
| 인과 | "A하면 B가 된다" |
| 수치·기본값 | 일부는 R8이 이미 본다 |

목록을 만든 뒤 하나씩 코드로 확인한다. 그래야 "읽었다"가 아니라 **"14개 중 14개 확인"**이 되고, 확인 못 한 게 남으면 드러난다.

한 기능의 문서만 대상으로 하면 주장이 10~20개라 전수 확인이 가능하다. 문서 전체를 한 번에 하려 들면 훑고 지나가게 된다.

### 상태 수명 표를 반드시 채운다

기능이 들고 있는 상태가 생명주기 이벤트에서 어떻게 되는지 표로 채운다. **빈칸이나 "확인 안 됨"이 곧 발견이다.**

| 이벤트 | 이 기능의 상태는? |
|--------|------------------|
| 로그인 | |
| 로그아웃 | |
| 계정 전환 | |
| 앱 복귀 | |
| 프로젝트 재초기화 | |

채팅 구독 버그가 정확히 여기서 나왔다 — 로그아웃 칸이 비어 있었다.

### 정의만 있고 실행되지 않는 것을 찾는다

**소스에 있다고 도는 것이 아니다.** 리더보드 회차 전환 함수는 주석에 "cron 전용"이라 적혀 있고 전용 인덱스까지 있었지만 `cron.schedule` 이 어디에도 없어, daily 리더보드가 3일째 1회차에 멈춰 있었다. `purchase-verify-apple-legacy` 는 어느 프로젝트에도 배포된 적이 없었고, 코드도 없는 컬럼에 INSERT 해서 배포했어도 첫 호출부터 실패할 상태였다.

**둘 다 코드만 읽어서는 안 보인다.** 정의는 멀쩡하고 호출자가 없을 뿐이라 문법·타입·검사기 어디에도 안 걸린다. 라이브를 직접 조회해야 드러난다.

세로 점검마다 아래 셋을 확인한다.

| 확인 | 방법 |
|------|------|
| cron 전용 함수가 실제로 스케줄됐나 | `install.sql` 안쪽은 **R13이 자동으로 본다.** 라이브에 실제로 걸렸는지는 `select jobname, schedule, active from cron.job` 로 대조 |
| Edge Function 이 배포됐고 파일과 같나 | `list_edge_functions` 로 목록·`verify_jwt` 확인. `Samples~/DatabaseSetup/EdgeFunctions/` 의 디렉터리와 개수를 맞춘다 |
| 배포된 Edge Function 이 현재 스키마로 동작하나 | INSERT·SELECT 하는 컬럼을 `information_schema.columns` 와 대조. `not null` 컬럼을 빠뜨리지 않았나 |

**배포됐다고 동작하는 것도 아니다.** 필요한 시크릿(`APPLE_SHARED_SECRET` 등)이 없으면 설정 오류만 반환한다. 코드가 시크릿을 읽는 곳을 찾아 사용자에게 설정 여부를 확인한다 — 시크릿 값은 대신 넣지 않는다.

프로젝트가 둘 이상이면(ProjectR·DevilSlayer) **양쪽 모두** 본다. 한쪽에만 있는 함수가 곧 드리프트다. 배포 후에는 응답의 `ezbr_sha256` 이 프로젝트 간에 같은지로 같은 코드가 올라갔는지 확인할 수 있다.

### 진행 순서

1. `install.sql`의 해당 절을 읽고 **테이블·RPC·권한 목록을 만든다** (기준점)
2. 그 목록을 들고 Core → Facade → 파사드를 따라가며 대응 확인
3. 문서를 열어 **서술이 코드와 맞는지** 읽는다 (검사기가 못 보는 부분)
4. 샘플과 Retool이 실제로 쓰는지 확인
5. 상태 수명 표를 채운다
6. **cron·Edge Function이 실제로 걸려 있고 동작 가능한지 라이브에서 확인한다**
7. 발견 목록을 3분류해 보고

읽기 위주라 중간에 멈춰도 발견 목록만 남기면 다음에 이어진다.

## 이 스킬을 고치는 것도 점검의 일부다

**점검 중에 실수하거나 헛발질하면 그 자리에서 반영한다.** 나중에 하지 않는다 — 세션이 끝나면 사라진다.

남기기 전에 두 가지를 판단한다.

1. **검사로 막을 수 있으면 규칙 대신 검사를 만든다.** 샘플이 `internal` 클래스를 부르던 실수는 "확인해라"는 규칙 대신 R6이 타입 가시성을 보도록 고쳐서 막았다.
2. **재발 범위를 본다.** 특정 경로에서만 쓰는 규칙이면 `.claude/rules/`에 `paths` 를 붙여 넣고, 이 리포지토리 전반이면 아래 함정 목록에, 어디서든 나는 도구 사용 실수(CRLF 치환·일괄 치환 확인 등)면 **전역 `~/.claude/CLAUDE.md`**에 넣는다.

## 함정 — 이 리포지토리에서 실제로 겪은 것

**`CLAUDE.md`를 믿고 코드를 고치지 않는다.** 문서가 코드보다 낡아 있을 수 있다. "SupabaseSDK는 MonoBehaviour singleton"이라는 서술을 믿고 샘플이 `internal` 클래스를 부르게 바꿔 컴파일이 깨진 적이 있다. **항상 코드로 먼저 확인한다.**

**`Samples~`는 import 전까지 컴파일되지 않는다.** Unity 컴파일 통과가 샘플 검증이 아니다. 샘플이 부르는 API의 존재 여부는 검사기 R6이 본다.

**`Runtime/Unity`는 컴파일 검증 수단이 없다.** `CoreCompileCheck`는 Core만 본다. 검사기는 구문 파싱이라 타입 해석·using 누락을 못 잡는다. 이 계층을 고쳤으면 **사용자에게 Unity 재컴파일을 요청한다.**

**파일을 지우면 `.meta`도 함께 지운다.** 새로 만들지는 않는다.

**라이브 DB와 `install.sql`은 갈라진다.** 실제로 세 번 발생했다(`mails.localized`·`ts_coupon_redeem`·`user_data_logs.source`). 신규 프로젝트를 만들 때까지 드러나지 않는다.

Supabase MCP로 ProjectR(`wxivrmvtpufeczltward`)과 다섯 가지를 대조한다.

| 대상 | 라이브 쪽 조회 |
|------|---------------|
| 테이블·컬럼 | `information_schema.columns` |
| 함수 | `pg_proc` + `pg_namespace` |
| 인덱스 | `pg_indexes` — `*_pkey`·제약이 만든 `*_key`는 제외 |
| RLS 정책 | `pg_policies` |
| RLS 활성화 | `pg_class.relrowsecurity = false` 인 테이블이 없어야 함 |
| cron 잡 | `cron.job` — `install.sql` 의 `cron.schedule` 호출과 개수·이름이 맞아야 함 |
| Edge Function | `list_edge_functions` — `Samples~/DatabaseSetup/EdgeFunctions/` 디렉터리와 개수가 맞아야 함 |

**테이블 제약이 만든 인덱스에 주의한다.** `constraint x unique (...)` 는 `create index` 문이 아니라서 `install.sql` 쪽 추출에 안 잡히는데 `pg_indexes` 에는 인덱스로 보인다. 드리프트가 아니다.

## 검사기 오탐이 나오면

**규칙의 예외를 검사기에 반영한다.** 오탐을 그냥 두면 경고가 신호 구실을 못 한다. 예외 목록은 `Tools~/SdkAudit/README.md`의 예외 표에 근거와 함께 남긴다.

**구분할 수 없는 규칙은 넣지 않는다.** 표 칸 부연 괄호 검사를 넣었다가 뺐다 — 수식 표기 `(i)`·버전 `(4.x)`·파라미터 목록과 구분이 안 돼 오탐이 20건 넘게 났다. **노이즈 있는 검사는 없느니만 못하다.**

반대로 검사기가 **놓친 것**을 발견하면 규칙을 추가한다.

**검사기를 고쳤으면 자체 테스트를 돌린다.**

```bash
dotnet run --project Tools~/SdkAudit -- --selftest
```

새 규칙을 추가하면 `SelfTest.ExpectedTags`에 태그를 넣고 픽스처에 위반 사례를 추가한다. **"통과"가 곧 "동작한다"는 뜻은 아니다** — R12를 붙였을 때 경로 필터가 너무 넓어 아무것도 잡지 못했는데 통과로 보였다.

## 끝낼 때

```bash
dotnet run --project Tools~/SdkAudit
dotnet run --project Tools~/SdkAudit -- --selftest
dotnet run --project Tools~/FailReasonCheck
dotnet build Tools~/CoreCompileCheck/CoreCompileCheck.csproj
```

문서를 건드렸으면 죽은 링크까지 확인한다.

```bash
cd docs~ && npx vitepress build
```

그리고 **메모리의 `project_sdk_audit_progress.md`를 갱신한다** — 끝난 것, 남은 것, 결정 대기 항목, 이번에 배운 함정. 컨텍스트가 압축돼도 여기서 이어갈 수 있어야 한다.

**대상을 다 돌았으면 결정 대기 목록을 사용자에게 제시한다.** 모아두기만 하고 안 꺼내면 미결이 메모리에서 조용히 늙는다.

**사용자에게 넘길 것을 한 묶음으로 정리한다.** 축마다 흩어 내보내지 말고 마지막에 모아서 낸다.

| 넘길 것 | 형태 |
|---------|------|
| Unity 재컴파일 | 어느 파일이 바뀌었는지와, Play Mode 에서 밟아볼 경로 |
| Retool 수정 | 파일 경로 + 줄 번호(1~2곳) 또는 전체 코드(3곳 이상). 게시는 사용자 |
| 배포·시크릿 | 되돌리기 어려우므로 **확인받고** 진행 |
| 커밋 | 축마다 커밋을 권한다 — 재컴파일이 실패했을 때 범인을 좁히는 유일한 수단이다 |

커밋 안 된 변경은 컨텍스트가 날아갔을 때 복구 수단이 없는 유일한 항목이다. 커밋·푸시는 사용자가 직접 한다.
