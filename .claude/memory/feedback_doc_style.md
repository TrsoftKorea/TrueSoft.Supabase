문서(Docs/VitePress) 작성·수정 시 아래 규칙을 모든 문서에 반영한다. 사용자가 방향성·스타일·구조를 한 번이라도 언급하면 **전역 규칙으로 간주하고 이 파일에 즉시 추가**한다(특정 페이지/문장 1회 수정 요청은 제외).

## 글쓰기 스타일

1. **개발자의 목적 기준으로 설명한다 (내부 구현 기준 금지)** — 가장 중요. 개발자가 **무엇을 이루려는지**(예: "Android에서 Apple 로그인 붙이기")를 중심으로 쓰고, SDK가 그걸 어떻게 처리하는지(브라우저·OAuth·딥링크·네이티브 브릿지·매니페스트·launchMode 등)는 기준으로 삼지 않는다. 내부 메커니즘은 "자동 처리, 할 일 없음" 수준으로만 언급하거나 생략. 기능·조건·제목을 메커니즘 용어("브라우저 로그인")가 아니라 목적·플랫폼 용어("Android 로그인")로 표현한다. 개발자가 설정 작업을 하려면 알아야 하는 값(어디에 무엇을 넣는지)은 설명하되, 그 값의 내부 의미를 설명하려고 기능 전체를 구현 관점으로 끌고 가지 않는다.
2. **페이지·항목 이름에 괄호 금지** — 헤딩(`# 인증 (Auth)` → `# 인증`)뿐 아니라 **사이드바 항목·홈 카드 제목·페이지 제목·콜아웃 제목 등 모든 "이름"에 괄호를 넣지 않는다**(`탈퇴 취소 (토큰)` → `탈퇴 취소`, `플랫폼 전용 생성 (선택)` → `플랫폼 전용 생성`, `인앱 결제 (IAP)` → `인앱 결제`). 부연이 필요하면 본문/설명 줄로 옮긴다. (본문 괄호는 허용)
3. **헤딩·제목에 한글/영어 혼용 금지** — `# 플레이나누 Migration` → `# 플레이나누 이관`. 한글 문서 헤딩은 한글로. 예외: 고유명사(Google·Apple·Supabase 등), 공식 약어(API·SSL·DB·IAP·URL·JSON 등), 백틱 안 코드 식별자.
4. **자동 실행 코드는 코드 블록으로 노출 금지** — SDK가 내부에서 자동 호출하는 메서드를 코드 예시로 보여주지 않는다(개발자가 직접 호출해야 하는 줄 오해). 동작은 산문으로 서술.
5. **변경사항·대화 맥락을 문서에 넣지 않는다** — "무엇이 바뀌었다/추가됐다"가 아니라 **처음부터 그렇게 동작하는 것처럼** 작성. 작업 중 대화에서 나온 정정·오해 바로잡기("`.p8` 파일 내용이 아니라 JWT를 넣습니다" 같은 'X가 아니라 Y')도 문서엔 넣지 않는다 — **올바른 동작(Y)만** 적는다. 내부 구현 메커니즘은 굳이 설명하지 말고 개발자 입장의 사용법·결과만. changelog식 섹션·콜아웃 남발 금지.
6. **병렬·연관 항목 함께 맞추기 (좁은 시야 금지)** — 한 항목을 손댈 때 같은 부류의 형제 항목에도 동일 적용되는지 점검하고 함께 처리. 하나만 고치고 비슷한 것을 빠뜨리면 통일성이 깨진다(예: 단일 함수 페이지의 trailing 호출 예제 유무도 형제끼리 맞춘다).
7. **warning 남발 금지 + 중복 제거** — `::: warning`은 정말 critical한 것(안 지키면 기능 깨짐·데이터 손실)만. 그 외(권장 순서·API 선택·일반 안내)는 사용법 톤으로. 이미 다른 섹션에 있는 중복 블록은 제거.
8. **하이핸드·생색 문구 금지, 필요한 내용만** — 개발자를 바보 취급하는 친절 설명·동기부여·당연한 안내를 넣지 않는다(예: "이미 대시보드에 와 있으니 같이 해두면 다시 안 들러도 됩니다", "~하면 편리합니다"류). 사실과 필요한 절차만 간결하게. 한 문장으로 충분하면 한 문장.
24. **함수 페이지엔 간단한 사용 예제를 포함한다** — 시그니처만 던지지 말고, 한 줄 설명 바로 다음(파라미터/반환/실패 표보다 **앞**)에 호출 예제 코드블록을 넣는다. **새 헤딩 없이 코드블록만**(단일 함수 페이지는 flat 유지). 액션형(`Task<SupabaseResult>`)은 `var result = await Supabase.Xxx(args); if (result.IsSuccess) { ... } else { ... }`, 데이터형(`Task<SupabaseResult<T>>`)은 `if (result.IsSuccess) { var x = result.Data; ... }`. 5~10줄, 시그니처·반환 표에 있는 것만 사용(없는 API 창작 금지, 게임측 UI 호출은 플레이스홀더). 이미 주 예제가 있으면 스킵. 기준 파일: `auth/anonymous.md`(액션형)·`mailbox/claim.md`(데이터형). (2026-07-15 auth·social·mailbox·withdrawal·display-name·remote-config 함수 페이지 38개 일괄 적용.)

25. **산문에서 "이런 기능에 쓰세요"라고 용도를 열거하지 않는다** — 금지 대상은 **설명 문장**이다. "출석·이벤트 기간·쿨다운 판정에 쓰세요", "제휴 코드처럼 ~할 때 씁니다", "방송이나 공지로 알리는 이벤트 코드가 여기 해당합니다", "씬 전환·로그아웃·앱 종료 등 ~ 순간에 사용하세요" 같은 문장을 쓰지 않는다. API가 **무엇을 하는지**와 **어떤 성질인지**만 적는다. 절 제목도 용도("남은 시간 표시")가 아니라 API 성질로 쓴다. SDK 문서가 게임 설계를 규정하는 것처럼 읽히고, 열거한 예에 안 맞는 개발자는 헷갈린다.
    - **예제 코드는 예외** — 예제 안의 게임측 호출(`GrantEventReward()`·`ShowToast()`·`AppendBubble()`)은 그대로 둔다. 값을 어디에 쓰는지 보여야 예제 구실을 하고, 사용자가 명시적으로 허용했다(2026-07-29).
    - SDK 자체 동작을 가리키는 용어(유저 데이터의 "쿨타임 자동 저장")도 용도 열거가 아니므로 허용.
    - 설정 조합의 결과에 이름을 붙이는 표 칸(리더보드 "이벤트 기간 동안만 도는 주기 랭킹")은 허용 — 용도 추천이 아니라 조합의 성격 서술이다.

26. **조용히 처리하는 내부 안전장치는 문서에 적지 않는다** — 중복 요청 병합(single-flight), 재시도, 내부 캐시 무효화처럼 **개발자가 아무것도 안 해도 되는 보호 장치**는 언급 자체를 뺀다. 적으면 "내가 뭘 신경 써야 하나?" 의심만 생긴다. 판정: 그 문장을 읽고 개발자가 **코드를 다르게 쓰게 되는가**? 아니면 뺀다. 사용자 명시(2026-07-30): "이건 개발자 입장에서 알지 못하게 조용히 처리하는 안전장치이기 때문이야."
    - 공개 파라미터(`forceRefresh`·`maxStale`·`minIntervalSeconds`)의 의미를 설명하려면 그 파라미터가 건드리는 메커니즘은 적어야 한다 — 이건 예외.
    - "게임이 따로 캐시를 만들 필요 없다"처럼 **게임이 코드를 덜 쓰게 되는** 결론은 허용.

## 구조·정리

9. **기능별로 페이지 분리 + 좌측 사이드바 트리** — 한 페이지에 여러 주제를 길게 담지 말고 기능(보통 H2) 단위로 페이지를 나눠, 좌측 사이드바에서 좁은 주제로 선택하게 한다. 페이지당 스크롤 최소화. 오른쪽 outline(책갈피)에 의존하지 않는다.
10. **기능 설명/개념 페이지는 과분할 금지 + "개요"로 통일** — "동작 방식" 같은 기능 설명 페이지는 잘게 쪼개지 말고 각 기능의 첫 페이지를 **"개요"**로 통일해 무슨 내용인지 짐작되게 한다. 짧은 개념 페이지가 흩어져 있으면 개요로 합친다.
11. **구별되는 주제를 묶지 않는다** — 서로 다른 주제를 `·`로 한 카테고리/그룹/항목에 어정쩡하게 합치지 않는다(예: "닉네임 · 프로필", "탈퇴 · 서버 이주" → 각각 분리). 단일 페이지 항목은 단일-항목 그룹 대신 직접 링크로.
12. **페이지 끝 매달린 구분선 금지** — 페이지 마지막 줄이 `---`로 끝나지 않게 한다(섹션 분할 시 남는 hr 제거).
13. **placeholder·TODO 금지** — "추후 업데이트 예정", "작성 예정" 같은 미완성 표시를 게시 문서에 남기지 않는다. 실제 내용으로 채우거나 항목 자체를 빼라. (예외: 사용자가 명시적으로 "준비 중"으로 남기라 한 항목 — 예: 우편함 API.)
14. **작업 페이지에서 개발자가 손댈 게 없는 내용·섹션을 뺀다** — how-to/설정 페이지에 "별도 작업이 없는 주제"를 쓰지 않는다. "~할 필요가 없다"를 긍정문("자동으로 처리됩니다")으로 바꾸는 걸로 끝내지 말고 **언급 자체를 삭제**한다. SDK가 자동 처리해 손댈 게 없는 섹션·항목(예: "Unity 빌드: 추가 작업 없음")은 통째로 뺀다. 비-액션 내용을 적으면 "이거 내가 해야 하나?" 의심만 생기고 분량만 는다. 정말 가치 있으면 작업 페이지가 아니라 설명 페이지(Rule 21)에만. 꼭 알려야 할 단서(예: 에디터 미지원)는 관련 기능 페이지에. (단 "영향이 없습니다" 같은 작업 범위·결과 사실 진술은 허용.)
15. **플랫폼·조건별 차이를 개별 항목/셀에 흩뿌리지 말고 한 섹션으로 묶는다** — "iOS만 ~", "Android만 ~" 단서를 표 셀·팁마다 분산시키지 않는다. 공통(기본) 설정을 먼저 쓰고, 특정 플랫폼에서만 추가되는 작업은 **"Android 추가" 같은 전용 섹션 하나에 모은다**. 그래야 나중에 그 플랫폼을 붙일 때 한 곳만 보면 된다. 입력해도 무해한 항목은 공통에 두되, 그 입력을 만드는 사전작업이 플랫폼 전용이면 그 작업과 함께 전용 섹션으로.
16. **문서 수정 후 그 페이지를 의미 단위로 다시 읽고 파급을 같은 턴에 잡는다** — 내용을 바꾸면(섹션 삭제·이동 등) **제목이 내용과 맞는지, 도입문·링크 텍스트·형제 페이지 참조가 여전히 맞는지**를 즉시 점검·수정한다. 사용자가 지적하기 전에 끝낸다. 렌더(`preview`) 확인은 "깨지지 않음"만 보장하지 제목-내용 불일치 같은 의미 오류는 못 잡으므로, 수정한 페이지는 반드시 전체를 다시 읽는다. 예: "Unity 빌드" 섹션을 지웠으면 즉시 페이지명 "대시보드·빌드 설정"의 "빌드"도 뺀다.

## 정확성

17. **참조 대상은 실제 존재해야 함** — 문서·README가 가리키는 파일·샘플·경로·메뉴는 실제로 존재하는 것만. 없는 파일에 대한 가이드(예: 별도 파일인 양 설명하지만 실제론 다른 파일 안의 클래스)를 만들지 않는다. 작성·수정 시 실제 파일/구조와 대조.
18. **자동 생성 파일을 직접 수정하라고 안내 금지** — `PlayerSave.cs`처럼 생성기가 덮어쓰는 파일에 코드를 넣으라고 안내하지 않는다. 비파괴 방법(공용 API·별도 partial 파일 등)을 안내한다.
19. **외부 웹 UI 경로·동작은 확신 없으면 추측 금지, 사용자에게 확인** — Supabase 대시보드·Apple Developer 등 외부 콘솔의 메뉴 경로·필드 이름·동작 절차를 정확히 모르면 그럴듯하게 지어내지 말고 사용자에게 묻는다. SDK는 **문서·코드의 정확도가 최우선**이며, 내(어시스턴트)가 묻지 않고 넘어가는 편의보다 중요하다. 스크린샷으로 확인된 것만 단정하고, 추측이면 추측이라 밝히고 확인 요청.
20. **UI 옵션·필드 설명은 화면의 실제 설명문을 정확히 옮긴다 (임의 의역·창작 절대 금지)** — 대시보드/콘솔의 토글·필드 뜻을 문서에 적을 때, 화면에 표시된 설명(tooltip/help text)을 **그대로 번역**한다. 추측으로 의미를 바꾸거나 그럴듯한 단어를 지어내지 않는다. 예: "Allow users without an email"의 화면 설명은 "공급자가 이메일을 반환하지 않을 때도 로그인 허용"인데, 이를 'Apple 이메일 숨김 사용자'라고 창작한 것은 오류. 화면 설명을 못 봤으면 Rule 19대로 확인부터.

## 자명한 서술 금지 · 독자 기준

23. **수정 요청 문구를 텍스트로 옮기지 않는다 — 독자는 사용자가 아니라 "SDK를 처음 보는 개발자"** (문서·주석·인스펙터 HelpBox·툴팁 공통). 사용자의 수정 요청은 작업 지시일 뿐이며, 그 내용을 그대로 받아 적으면 안 된다. 판정 순서: ① 외부 동작이 안 바뀌었으면(내부 구조 변경·리팩터) **아무것도 적지 않는다**. ② 바뀌었으면 이전과의 차이·경위가 아니라 **현재 동작을 처음부터 그랬던 것처럼**, 개발자가 쓰는 데 필요한 만큼만 적는다. ③ 화면·코드가 스스로 보여주는 자명한 것("목록은 읽기 전용", "편집은 CSV로" — CSV 버튼이 이미 보임, "제외 컬럼은 흐리게" — 코드가 그 자체)은 적지 않는다. 텍스트는 보이지 않는 것(왜 그런지, 숨은 제약, 다음 행동)만 담는다. 사용자 명시(2026-07-10): "수정 내용을 그대로 적지 말고, 이 SDK를 처음 보는 개발자 입장에서. 외부적으로 바뀐 게 없다면 굳이 적을 필요 없어."

## 적용 vs 설명 분리

21. **적용(how-to)과 설명(why)을 분리한다** — 설정·설치 같은 how-to 페이지는 **"그냥 따라 하면 되는 동작"만** 담는다. 처음 읽는 개발자는 이유를 다 이해하려는 게 아니라 우선 적용부터 하려 한다. "왜 이렇게 하는지", 배경 원리, 자주 나는 오류 설명은 **별도 설명 페이지로 빼고**, 적용 단계에서 그 페이지로 **링크만 남긴다**(필요하면 `#anchor`로 항목 지정). how-to에 긴 warning/배경 콜아웃을 쌓지 않는다. 단, 안 따르면 바로 깨지는 **동작 지시 자체**(예: "Services ID를 맨 앞에")는 how-to에 남기되 이유는 링크로.
22. **설명·상세 페이지는 사이드바에서도 작업 흐름과 분리한다** — Rule 21로 분리한 설명/상세/배경 페이지(예: "Apple 설정")는 해당 기능의 사이드바 그룹(작업 흐름) 안에 두지 않는다. 처음 따라 하는 사람이 흐름에서 마주치지 않도록, **사이드바 최하단의 별도 "상세 정보" 그룹(접힘)에 모으거나 링크 전용**으로 둔다. 이런 페이지는 구현 방법이 아니라 다른 이유로 일부러 찾아오는 경우라, 작업 항목들 사이에 끼우지 않는다.

**Why:** 사용자가 세션 내내 "내부 구현 말고 개발자 목적 기준", "비-액션/할 일 없는 내용 빼기", "적용·설명 분리", "플랫폼 차이는 한 섹션", "외부 UI는 추측 말고 확인", "화면 설명 원문 그대로", "수정 후 파급 점검", "헤딩·이름 괄호/혼용 금지" 등을 반복 지시. "1회 수정 요청만 빼고 전부 규칙화"하라고 명시.
**How to apply:** 문서 작성·수정마다 위 규칙 전체(1~22)를 점검. 수정한 페이지는 끝까지 다시 읽어 파급(제목·링크·형제)을 잡는다. 새 방향성 지시가 나오면 이 파일에 즉시 추가. VitePress 죽은 링크는 `npx vitepress build` 또는 preview로 검증.
